**1. Verdict**
Arm C can show that rules blended into r2's argmax move the Ryu gate, but as written it cannot show the thing the plan claims: that a memory *augments* System 1. With `DEFAULT_WEIGHT=0.5` and argmax, a matching rule always wins (see §4), so arm C measures "a 10-line scripted bot beats a Dhalsim-only checkpoint vs Ryu" — likely true, uninformative. Biggest weakness: no arm separates "rules help laya" from "rules replace laya", and the 0.5 s grading horizon will drop exactly the rules (jump-ins, throws) that made the teacher good.

**3. Gaps**
- **Multi-worker vs "in order".** The gate protocol pairs openings by `--workers 4 --seed 4242` (worker i, match e → i·30+e+1 idle frames). Arm B "20 matches played in order, memory growing" with 4 concurrent processes means matches 1–4 share one memory and four processes race on `inbox.txt`/`memory.txt`. Single-worker changes the openings → unpaired. Decide: single worker for all three arms (re-run control), or per-worker memories (then n=5 per curve).
- **Paired design, unpaired SE.** Lockstep + same opening means arms diverge only at the first changed decision; use the SE of per-opening paired differences, not `sqrt(se_a²+se_b²)`. 2 unpaired SE ≈ 24 net damage; paired will be far tighter or reveal true noise.
- "B's per-match curve rises": 20 points, per-round sd ≈ 30 — no test named. Drop it or predeclare one.
- Matches 11–20 vs 1–10 confounds memory growth with opening order; compare B(11–20) against A(11–20) only, which the text half-says.
- Per-opponent RAM checks missing. JOURNAL lists walls, projectile slot, struct layout as prerequisites per opponent; `fireball` was verified on yoga fire only. Vs Ryu the field may be silent on hadoukens; r2 has never seen one. Phase 1.2 checks only clock/bars/controllable.
- **Surprised floods.** `taken_next>0` over a 30-frame window tags ~7 consecutive decisions per hit; 5–7 hits/round → 15–20% of decisions, all "surprised", most not causal. Use the first decision of each window or `big_hit`.
- Correlated uses: a rule matching `opp_state=jump dist=mid` fires on every 4-frame decision through the jump; 20 "uses" ≈ 3 jumps. The 1-SE drop is meaningless with that dependence, and 1 SE drops a good rule 16% of the time under the null anyway.
- "34 unit tests": `tests/test_contract.py` has 16 test functions; parametrized count unverified.

**4. Design flaws**
- **Blend is an override.** Under argmax the rule's move wins iff `λ > (1−λ)(p_top − p_m)`. With λ ≥ 0.5 it always wins (max gap is 1). Decision §3 "no rule overrides the hands" is false at the default weight. Either sample from p, or define λ as the gap threshold explicitly.
- **Grading horizon < payoff.** `NEXT_WINDOW=30`. A jump-in's kick lands after the arc (~40+ frames); walk-into-throw needs two decisions. The grader will drop the teacher's best tactics and keep only instant pokes. Grade to the end of the macro's consequence (≥ 1 s) or per round.
- **Uninformative uses.** When laya's argmax already equals the rule's move, the use carries no information about the rule. Log "fired" and "changed" separately; grade on changed only. Baseline should be matched on the rule's full condition set, not just `opp_state`+`dist`.
- Diagram says "first rule that matches"; text says most-specific. Pick one.
- `last=` conditions allow self-sustaining loops (`last=lp -> lp`).
- Round-2+ reproducibility from "opening + memory" is false in arm B: round 2's state depends on round 1's play under a different memory.
